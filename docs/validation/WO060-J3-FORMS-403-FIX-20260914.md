# WO-060 — Correction des refus 403 des formulaires J3

Statuts : `EXPERIMENTAL`, `LOCAL_ONLY`, `NOT_PRODUCTION_APPROVED`, `NO_CRITICAL_DEPENDENCY`.

## Symptôme et cause

Le 14 septembre 2026, l'opérateur signale HTTP 403 dans Chrome après soumission des quatre
actions du tableau de bord : `/j3/settings`, `/j3/plans`, `/j3/collect` et `/j3/import`.
Une lecture HTTP du Lab actif confirme que le tableau de bord répond 200 avec
`Referrer-Policy: no-referrer`.

Le contrôle local des routes J3 exige une origine HTTP identique au Host autorisé lorsqu'un
en-tête Origin est présent. Chromium transforme l'origine de ces POST de navigation en
`null` lorsque la page applique `no-referrer`. L'intercepteur refuse alors le POST avant
l'accès au contrôleur, au jeton, à la modification des paramètres ou au départ d'une collecte.

Les pages live et de réarmement avaient déjà une politique adaptée. L'ajout des formulaires
J3 avait omis les deux routes du tableau de bord, `/` et `/dashboard`, dans cette sélection.
Les tests MVC précédents envoyaient surtout des POST sans Origin et ne couvraient donc pas
le comportement natif du navigateur.

## Correctif

`SecurityHeadersFilter` applique `Referrer-Policy: same-origin` aux deux routes du tableau de
bord, y compris avec un identifiant de session dans l'URL et un contexte applicatif.
Les pages adjacentes gardent leur politique précédente. Les scripts restent désactivés sur
le tableau de bord, les formulaires restent limités à la même origine et le cache reste interdit.

L'intercepteur n'est pas modifié : origine étrangère, origine `null`, hôte différent ou
mauvais jeton continuent d'être refusés. Les POST légitimes utilisent le contrôleur existant.
Le même changement couvre paramètres, création/modification/annulation des horaires, collecte A,
import B et contrôle de nettoyage depuis le tableau de bord.

À la demande de l'opérateur, le bouton devient **B. Importer et valider J3 — ZÉRO APPEL**.
Le test du rendu et les instructions de recette suivent ce libellé.

Aucun changement de schéma, de préférence persistée, de donnée de collecte, de worker,
de capacité V11 ou de configuration Eclipse n'est nécessaire pour ce correctif.

## Vérification

- Reproduction avant correction : `SecurityHeadersFilterTest` échoue sur les six nouveaux cas
  de tableau de bord, avec `no-referrer` au lieu de `same-origin`.
- Tests HTTP : origine locale exacte sur les deux hôtes ; case automatique décochée et heure
  vide en mode démarrage ; heure fixe ; création, révision et annulation d'un horaire ;
  collecte multipart A avec double clic refusé ; import B ; origine étrangère ou opaque refusée.
- Application Web complète et PostgreSQL jetable : les trois cas de `J3WebApplicationIT`
  passent. Ils vérifient l'import durable, la désactivation, la réactivation à heure fixe,
  la relecture des préférences et les transitions des horaires avec les vrais jetons/formulaires.
  Le fournisseur est désactivé et sa fabrique est doublée ; aucune interaction n'est admise.
- Chromium natif : **32 cas validés**, soit deux hôtes × deux pages × quatre actions × deux
  politiques. Les 16 cas `no-referrer` reproduisent `Origin: null` et 403 ; les 16 cas corrigés
  présentent l'origine locale exacte et franchissent le contrôle.
- Validation globale : **PASS**, `mvnw.cmd clean verify`, terminé le 14 septembre 2026 à
  **09:48:03 UTC** en **13 min 25 s**. Les rapports XML comptent **2 387 tests Surefire**, dont
  cinq exclusions prévues, et **278 tests Failsafe**, sans exclusion. Aucun échec ou erreur.

Les cinq exclusions standard sont les quatre cas de liens symboliques soumis aux capacités
Windows et la qualification native J6 à activation distincte, déjà documentés pour WO-060.
Les trois scénarios Web J3/PostgreSQL sont tous exécutés, sans exclusion. Le journal complet
porte le SHA-256 `2d45d5aa65cdbc3e329198459e22ed6c1113b1b035563a76d412501c4ad23ae8`.
Le diff, l'encodage UTF-8, l'absence de secrets et le maintien de `server.address=127.0.0.1`
ont aussi été vérifiés. Le script de qualification est analysé par le parseur PowerShell.
Son exécution complète avec le cache Chromium local existant termine aussi avec les 32 cas
validés ; le relevé versionné lie les empreintes du programme Java, du script et de son journal.

Le [relevé Chromium](WO060-J3-FORMS-BROWSER-20260914.json) contient les 32 observations sans
corps de formulaire, jeton ou cookie. Le banc utilise le filtre et l'intercepteur de production,
avec des formulaires synthétiques ; son statut 200 signifie que le contrôle autorise le POST.
La redirection 302 des contrôleurs réels et les écritures SQL sont vérifiées séparément par MVC.

Le banc livré force le contexte Chromium **hors ligne** et répond en mémoire à chaque requête.
Il n'utilise pas le profil de navigation de l'opérateur et ne contacte ni son Lab ni le fournisseur.
Les premières versions du banc, non retenues comme preuve d'isolement, autorisaient des redirections
qui pouvaient provoquer des GET du tableau de bord actif ; aucun POST n'était transmis au Lab.
La version qualifiée supprime ces redirections et impose le mode hors ligne.

Les échecs intermédiaires des tests ont aussi permis d'aligner l'ancienne assertion « 5B » et
de rendre le test d'import indépendant des horaires créés par les nouveaux cas dans la même base
jetable. Il vérifie désormais la conservation des ordres existants et l'ajout du seul import attendu.

## Commandes et traces

Depuis le worktree WO-060 :

~~~powershell
.\mvnw.cmd -Dtest=SecurityHeadersFilterTest test
# Avant correction : 6 échecs attendus.

.\mvnw.cmd "-Dtest=SecurityHeadersFilterTest,J3AutomationControllerTest,DashboardControllerTest,ProviderAccessControllerTest" test

.\mvnw.cmd "-Dtest=SecurityHeadersFilterTest,J3AutomationControllerTest,DashboardControllerTest,ProviderAccessControllerTest" "-Dit.test=J3WebApplicationIT" verify

.\mvnw.cmd clean verify
~~~

Le profil standard de ce dépôt exécute aussi Failsafe. Aucune migration ni implémentation
de persistance n'est changée dans ce correctif ; le second cycle redondant
`-Pintegration-tests verify` n'est donc pas nécessaire.

La qualification Chromium est volontairement distincte des tests standards. Après le build,
la commande suivante réutilise un cache Chromium déjà installé, sans installation automatique :

~~~powershell
.\scripts\Invoke-J3BrowserOriginQualification.ps1 -BrowserCachePath <cache-local-existant>
~~~

Le script utilise le profil historique `j7-browser-origin-loopback-qualification` uniquement
pour résoudre les dépendances de test via `dependency:build-classpath`. Il ne lance aucun test
J7, serveur ou parcours fournisseur. Il exécute ensuite explicitement
`scripts/qualification/J3BrowserOriginCheck.java` avec Java 25.

Traces locales ignorées : `.tmp/wo060-j3-settings-red.log`,
`.tmp/wo060-j3-forms-targeted.log`, `.tmp/wo060-j3-forms-web-verify.log`,
`.tmp/wo060-j3-forms-clean-verify.log` et `.tmp/wo060-j3-browser-origin.log`.

applicatifs et les quatre fichiers de tests modifiés. `git apply --check` réussit sur cette
copie HUMAN. Ce contrôle n'applique aucune modification à la copie Eclipse.
Le SHA-256 du patch est `36d402431f0b442b67447e0d09905f82b68376839192ce1bb87d5bc304ad215e`.
Les sources du correctif, les preuves et la documentation restent dans le worktree WO-060.

Pour reprendre l'essai opérateur, arrêter le Lab, appliquer le patch au projet utilisé par
Eclipse, actualiser ce projet, recompiler et relancer. Revenir ensuite à
`http://localhost:8087/` ou `http://127.0.0.1:8087/` et recharger le tableau de bord.
Un ancien onglet peut conserver la politique HTTP ou un jeton de la précédente instance.
Rejouer d'abord l'enregistrement des préférences ou d'un horaire futur ; le bouton d'import doit
afficher « B ». Les collectes fournisseur restent des actions opérateur distinctes.
